# AGENTS.md

This file provides guidance to AI agents when working with code in this repository.

## Non-Negotiable Runtime Rules

- **Never start the dev server.** The local dev server is already managed by the user at `localhost:3000`.
- **Never run `npm run dev`, `npm run preview`, default `docker compose up`, or any command that starts the local app unless the user explicitly asks.**
- The user owns the running local instance. Agents may build, test, lint, format, inspect files, and run non-server scripts.

## Project Overview

This is **Date Planner**, a single-package TanStack Start app for generating date ideas from user preferences. It uses React 19, Vite, TanStack Router, Tailwind CSS v4, Google Places, optional Ticketmaster event results, optional OpenAI reranking, and Redis-backed API response caching.

The app is URL-state driven: form/search state is represented in route search params, validated by schemas, and consumed by server functions that call external providers.

## Development Commands

All commands should be run from the repository root. The project uses `npm` as the package manager.

### Installation

```bash
npm install
```

### Building And Running

```bash
# Build production assets
npm run build

# Start production output after a build
# Only run when explicitly requested by the user.
npm run start
```

Do not run the development server:

```bash
# Do not run as an agent.
npm run dev
```

### Formatting, Linting, And Type Checking

```bash
# Check formatting
npm run format

# Lint source files
npm run lint

# Auto-fix formatting and lint issues
npm run check
```

There is no dedicated `typecheck` script. Use `npm run build` when TypeScript validation is needed.

### Testing

```bash
# Run the full Vitest suite
npm run test
```

### Cache Utilities

```bash
# Flush API cache with the default prefix
npm run cache:flush

# Flush API cache with a custom prefix
npm run cache:flush -- date-planner:dev
```

### Agent Hooks

After finishing code edits, run the post-coding hook to format and auto-fix lint issues:

```bash
bash .opencode/post-agent-hook.sh
```

## Architecture

### Core Components

1. **Routes (`src/routes/`)**

   - File-based routes managed by TanStack Router.
   - `src/routes/__root.tsx` defines the root shell.
   - `src/routes/index.tsx` owns the main question flow and search validation.
   - `src/routes/results.tsx` renders result-focused views.
   - `src/routeTree.gen.ts` is generated and must not be edited manually.

2. **Router Wiring (`src/router.tsx`)**

   - Creates the TanStack Router instance.
   - Integrates the generated route tree.

3. **Question Flow (`src/components/questions/`)**

   - `QuestionForm.tsx` coordinates the multi-step flow.
   - `QuestionFieldRenderer.tsx` maps question config to field components.
   - `question-config.ts` defines question metadata and options.
   - `hooks/useQuestionSearchState.ts` and `hooks/useDatePlanSubmission.ts` keep UI state aligned with route search params.
   - `fields/` contains individual input components.

4. **Server Functions (`src/server-functions/`)**

   - `index.ts` contains provider orchestration, Google Places calls, and optional OpenAI reranking.
   - `ticketmaster.ts` contains Ticketmaster integration.
   - `api-cache.ts` contains Redis cache helpers for provider responses.

5. **Schemas And Types (`src/schemas/`, `src/types/`)**

   - Zod schemas validate route/search state and server-function inputs.
   - `src/types/index-route.types.ts` contains shared route-related types.

6. **Constants (`src/constants/`)**

   - Suggestion lists and activity group definitions used by the question flow and provider logic.

7. **Styling (`src/styles.css`, `STYLE_GUIDE.md`, `TAILWIND_STYLE_REFERENCE.md`)**

   - Global Tailwind and CSS custom properties live in `src/styles.css`.
   - Design-system guidance lives in `STYLE_GUIDE.md`.
   - Pre-approved Tailwind patterns live in `TAILWIND_STYLE_REFERENCE.md`.

### Key Architectural Patterns

- **URL-driven state**: Search/form state uses `Route.useSearch()` and `navigate({ search })`. Changes to form fields must stay in sync with `SearchState` and route search validation in `src/routes/index.tsx`.
- **Schema-aligned options**: If UI options change, update the schema, exported types, question config, and server-side filtering logic together.
- **Provider field-mask discipline**: Google Places fetches use `places:searchText` with required field masks. Keep requested fields aligned with downstream type usage.
- **Graceful provider fallback**: OpenAI reranking is optional and should fail gracefully when `OPENAI_API_KEY` is missing or unavailable.
- **Server-only secrets**: Provider credentials and Redis URLs must stay server-side. Browser code must never receive secrets.
- **Generated route tree**: `src/routeTree.gen.ts` is auto-generated by TanStack Router and marked readonly in `.vscode/settings.json`. Do not edit it manually.

## Styling Rules

Read `STYLE_GUIDE.md` before creating or modifying any UI component.

Reference `TAILWIND_STYLE_REFERENCE.md` for tested Tailwind class patterns before inventing new component styling.

Use semantic CSS custom properties where possible:

```css
var(--ui-text)
var(--ui-surface)
var(--ui-border)
var(--love-700)
```

Avoid raw hex values unless the style guide documents a reason, such as Tailwind arbitrary-value limitations in gradients or shadows.

Selectable chips for date time, price level, distance presets, and similar controls should share the existing selected/unselected pattern from the question field components.

## Adding Or Changing UI Fields

When changing a user-facing option or adding a field, check every affected layer:

1. `src/schemas/index.schema.ts`
2. `src/types/index-route.types.ts`
3. `src/components/questions/question-config.ts`
4. Relevant component in `src/components/questions/fields/`
5. `src/components/questions/hooks/useQuestionSearchState.ts`
6. `src/routes/index.tsx` search validation
7. Server-side filtering or provider logic in `src/server-functions/index.ts`

For date-time options specifically, `dateTimeSchema` currently allows `Morning | Afternoon | Evening | Late Night | Now | Anytime`. Keep the schema, `DateTimeOption` type, UI options, and server filtering in sync.

## Environment Configuration

The development server command is wrapped with 1Password CLI:

```bash
op run --env-file .env -- vite dev --port 3000
```

Agents must not run it.

Important environment variables:

| Variable | Purpose |
| --- | --- |
| `GOOGLE_PLACES_API_KEY` | Required for Google Places results |
| `TICKETMASTER_API_KEY` | Enables event results |
| `OPENAI_API_KEY` | Enables AI reranking; app falls back if missing |
| `REDIS_URL` | Enables Redis-backed API response caching |
| `API_CACHE_ENABLED` | Enables or disables cache behavior |
| `API_CACHE_BYPASS` | Skips cache reads and writes fresh responses back |
| `API_CACHE_PREFIX` | Prefix for cache keys |
| `API_CACHE_DEFAULT_TTL_SECONDS` | Default cache TTL |

`.env` is 1Password-generated and manual edits are overwritten. Never commit `.env`, `.env.e2e`, API keys, Redis credentials, or other secrets.

## Docker And Redis

Redis is used as a server-side cache for external provider API responses. The browser must never connect to Redis or receive Redis credentials.

Agent-safe Redis command that prevents Docker Compose from reading `.env`:

```bash
COMPOSE_DISABLE_ENV_FILE=1 docker compose up -d redis
```

Do not run default `docker compose up` unless explicitly requested because it starts a development app service. If using the production Docker profile, target the production service explicitly so the default hot-reload app service is not started on the same port.

## Important Notes

- Imports can use the `#/*` alias defined in `package.json` for `src/*`.
- The package is ESM (`"type": "module"`).
- Tailwind v4 is integrated through `@tailwindcss/vite`.
- Tests use Vitest with jsdom support.
- Linting uses TanStack ESLint config.
- Formatting uses Prettier with the Tailwind plugin.
- Keep changes minimal and aligned with existing patterns.
- Do not add compatibility layers unless there is a concrete need.

## Verification Expectations

For code changes, run the narrowest useful verification first. Prefer this order:

1. `bash .opencode/post-agent-hook.sh` after edits
2. `npm run test` when behavior or logic changed
3. `npm run build` when route, server function, type, or integration changes need TypeScript/build validation

If a command cannot be run safely or fails because of missing local secrets/services, report that clearly with the relevant output.
